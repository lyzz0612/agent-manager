# 用户已拍板项

本文档记录当前已经明确拍板的产品、技术和交付约束。后续若有变更，应同步更新本文件与对应 OpenSpec 文档。

## 1. 产品边界

- Phase 1 只支持 `Cursor`
- 单用户
- 不做对话、session、终端托管
- Phase 1 重点是安装、账号、配置、已有 user 级 skill 管理
- 首页先做轻量状态页，复杂能力进子页面

## 2. 运行时与安装

- Cursor 运行时位于容器内受管目录
- 安装方式为运行时安装，不预装在镜像中
- 安装由网页手动触发
- 升级由网页手动触发
- 卸载不进入 Phase 1
- 安装来源优先官方在线来源
- 首次安装默认最新版
- 安装失败先直接报错，不做自动重试

## 3. 登录与账号

### 3.1 管理页

- 管理页使用固定访问 Token
- 用户通过登录页输入 Token 进入系统
- 生产环境必须显式传入 Token
- 开发态允许默认 Token

### 3.2 Cursor

- Cursor 登录流程采用“网页引导 + 外部完成关键步骤 + 回到网页确认”
- 当前用户信息展示先按最小目标做：
  - 已登录状态
  - 邮箱
  - 显示名
- 账号字段获取必须按 best-effort 处理，不能强假设

## 4. 配置与 Skill

- 配置管理采用双轨模式：
  - 已知字段表单化
  - 未知字段走原始文件编辑
- 原始配置文件保存前必须先预览
- Phase 1 不做自动备份
- Phase 1 只管理已有 skill
- skill 支持列出、查看、编辑、删除
- skill 编辑采用原始文件方式
- skill 删除使用普通二次确认
- 不做 skill 导入

## 5. 技术栈与结构

- 技术栈：`Rust + Axum + React/Vite + SQLite + Tauri`
- 仓库结构：`apps/ + crates/` monorepo
- Phase 1 只给桌面端留最小占位
- 未来桌面端尽量复用同一套 React UI
- SQLite 只承担轻量状态缓存和系统设置，不做历史记录

## 6. Docker 与部署

- `core + web` 单容器部署
- Compose 只提供应用容器
- 反向代理和 HTTPS 由外层处理
- 官方 Compose 默认不带挂载
- 官方 Compose 默认拉 `latest`
- 挂载由用户自行添加
- 目标镜像架构只有 `linux/amd64`

## 7. 发布与版本

- 只有当前分支 push 才触发 Action
- 普通提交也生成正式 `X.Y.Z`
- 根目录 `VERSION` 是唯一权威版本源
- Action 构建后自动回写 `VERSION`
- 回写提交通过 actor guard 跳过再次触发
- 手动发布和 tag 发布都要回写 `VERSION`
- 版本 tag 格式为 `vX.Y.Z`
- 镜像发布到 `ghcr.io`
- 普通提交也更新 `latest`
- 不保留分支别名标签
- 不保留 `sha-*` 辅助标签

## 8. 本机开发与验证

- 开发态和 Compose 验收是两个同等重要的入口
- 本机快启入口可以先偏 Windows，允许用 `.bat`
- 开发态默认接真实 Cursor 运行时
- 同时希望尽量支持在 Docker 中运行，避免污染宿主机

- 当前 `add-cursor-vps-manager` 继续作为 Phase 1 总变更是合理的，因为基础骨架、交付链路和管理页主流程仍然彼此强耦合
- 当安装/升级、真实 Cursor 登录探针和配置文件兼容性进入深水区后，建议再拆出更细粒度变更：
  - 独立桌面端变更：只关注 `apps/desktop` 与 Tauri 宿主集成
  - 细粒度 Cursor 集成变更：分别处理运行时安装、账号状态解析、配置/skill 兼容性
- 在当前阶段先保留单一 Umbrella 变更，避免过早拆分造成 README、部署链路和共享 Rust core 的上下文割裂
