## 上下文

当前仓库仍处于启动阶段，尚未形成正式的产品文档、实现骨架和交付流程。本次变更的目标不是继续讨论一个泛化的 agent 平台，而是把 Phase 1 收敛为一个面向 VPS 的 Cursor CLI 管理器，并把目前已经拍板的约束写成可执行设计。

当前约束已经比较明确：
- 单用户
- 只支持 Cursor
- 不做对话、session 和终端托管
- 运行时安装到容器内受管目录
- 以 `Rust + Axum + React/Vite + SQLite` 为主技术栈
- 当前分支 push 触发 GitHub Actions，自动递增 `VERSION` 并发布 `ghcr.io` 镜像
- 当前阶段同时需要项目文档体系，而不是只写少量部署说明

本设计需要同时解决三类问题：
- 产品边界：Phase 1 做什么，不做什么
- 交付边界：如何通过单容器、Compose、CI/CD 和本机快启形成闭环
- 文档边界：如何把 README、项目说明、技术方案、拍板项和文档索引正式沉淀下来

## 目标 / 非目标

**目标：**
- 定义一个适合 Phase 1 的单容器 Web 管理架构，用于管理容器内受管的 Cursor 运行时
- 明确账号、配置、skill、安装升级、发布流程等模块边界
- 为未来 Tauri 桌面端保留复用 React UI 和 Rust Core 的边界，但不在本次实现桌面功能
- 把用户已拍板的关键约束固化为项目级文档和 OpenSpec 规范
- 将实现拆成可分阶段推进的任务块，避免一口气做成大杂烩

**非目标：**
- 支持多用户、多租户或复杂权限系统
- 支持多个 CLI 或通用插件市场
- 托管对话、终端会话、任务编排或后台 agent 流程
- 在 Phase 1 中实现卸载、skill 导入、完整桌面端或复杂审计系统
- 假设一定能够从 Cursor 中拿到完整用户身份信息；身份展示按 best-effort 处理

## 决策

### 1. 以单个 Umbrella 变更覆盖 Phase 1，再按任务块推进实现

本次 OpenSpec 变更 `add-cursor-vps-manager` 作为 Phase 1 的总变更，统一描述产品、技术和交付边界。原因是当前仓库仍为空白状态，先拆成多个平行变更会让 README、技术方案、交付链路和运行时能力失去统一上下文。

替代方案：
- 一开始拆成多个独立变更：边界更细，但在仓库没有任何基线时会导致重复定义
- 只写文档不写总变更：缺乏后续实现入口，无法顺利过渡到 `tasks`

### 2. 采用 `Rust + Axum + React/Vite + SQLite`，并以 `apps/ + crates/` 组织 monorepo

服务端和宿主能力使用 Rust，前端使用 React/Vite，状态缓存和系统设置使用 SQLite。仓库从一开始按 monorepo 组织，为后续 `desktop` 占位但不立即初始化完整 Tauri 应用。

原因：
- 本产品的核心难点在文件系统、安装流程、子进程调用和未来桌面复用，而不是纯 Web 表单
- Rust Core 未来可同时服务 VPS Web 和 Tauri Desktop
- 现在先放入结构边界，后续不会因为仓库形态反复重构

替代方案：
- Node 全栈优先：上手快，但未来桌面宿主能力容易分叉
- 单应用简化结构：短期简单，后续拆分成本高

### 3. Phase 1 采用单容器部署，Axum 同时托管 API 和前端静态资源

生产部署形态为一个应用容器，内部包含 Rust 服务和打包后的 Web 前端。Compose 只提供最小应用容器，不内置反向代理，HTTPS 和公网暴露由外层自行处理。

原因：
- 用户明确要求 `core + web` 一起 Docker 部署
- 当前是单用户 VPS，不需要为扩缩容和网关分层过度设计
- 本机 compose 验收与线上部署形态可以保持一致

替代方案：
- 前后端双容器：更细致，但当前收益不大
- 内置 Caddy/Nginx：部署更全，但会把反代和证书责任强加到项目内部

### 4. Cursor 运行时位于容器内受管目录，采用运行时手动安装与手动升级

容器镜像默认不预装 Cursor。管理员在网页中手动触发安装，系统从官方在线来源安装最新版到受管目录。升级同样手动触发；Phase 1 不做卸载。

原因：
- 用户已明确要求运行时安装、官方在线来源、默认最新版
- 运行时安装可以减少基础镜像耦合和版本锁死
- 手动安装/升级符合当前“管理器”定位，也能降低误操作风险

替代方案：
- 镜像构建时预装 Cursor：启动更快，但会增加镜像维护成本
- 自动升级：运维更轻，但当前阶段不利于可控性
- 支持卸载：属于后续生命周期能力，不是 MVP 核心

### 5. 账号分为两层：管理页 Token 认证与 Cursor 登录引导

管理页自身通过固定 Token 登录页进入。生产环境必须显式传入 Token；开发态可使用默认 Token。Cursor 账号登录不与管理页登录混用，而是作为被管理对象处理。

Cursor 登录流程采用“网页引导 + 允许外部完成关键步骤 + 回到网页确认”的模式。系统以 best-effort 展示当前 Cursor 账号的已登录状态、邮箱和显示名；如果底层能力不足，则不能强行假设字段完整。

原因：
- 单用户 VPS 场景下，固定 Token 足够简单直接
- 各 CLI 登录流程差异很大，Phase 1 不能把 Cursor 登录抽象成通用表单
- 用户已经明确指出“明确的登录用户”是目标，但字段可用性要接受现实约束

替代方案：
- GitHub OAuth 或反向代理 SSO：安全性更强，但会增加额外系统依赖
- 将 Cursor 登录彻底封装成纯后端接口：无法反映真实的多步交互

### 6. 配置和 skill 管理采用“表单 + 原始文件”双轨模型

已知关键配置项通过表单化方式编辑；未知配置统一通过原始文件编辑区处理。原始文件保存前必须先预览再提交，但 Phase 1 不做自动备份。

已有 user 级 skill 支持列出、查看、编辑和删除；编辑采用原始文件直接修改，删除采用普通二次确认。Phase 1 不做 skill 导入或启停模型。

原因：
- 纯原始文件编辑对新用户不友好，纯表单又无法覆盖所有配置
- 双轨模型可以兼顾受控体验和自由度
- skill 先管理已有内容，可以显著压缩第一阶段范围

替代方案：
- 全部表单化：覆盖面不足
- 全部文件化：入口成本高
- 引入 skill 仓库/导入：超出 MVP 边界

### 7. 交付链路采用当前分支驱动的 CI/CD 与简单版本规则

当前分支 push 触发 GitHub Actions。普通提交也会生成正式 `X.Y.Z` 版本号，并更新 `latest`。根目录 `VERSION` 是唯一权威版本源；Action 构建后自动回写 `VERSION`，并通过 bot actor guard 防止回写再次触发。

镜像只发布到 `ghcr.io`，只构建 `linux/amd64`。官方 Compose 示例默认使用 `latest`，默认不带挂载，挂载由使用者自行添加。

原因：
- 用户明确要求“当前分支 push 生效”，不围绕 main 设计
- 当前仓库仍在快速试验阶段，简洁优先于长期发布治理
- `VERSION` 独立于具体语言清单，更适合 monorepo

替代方案：
- 只在 tag 或手动发布时生成语义版本：不符合用户要求
- 使用 `Cargo.toml` 或 `package.json` 作为版本源：对多端结构约束过强
- 额外保留 branch/sha 标签：用户已明确不要

### 8. 文档体系是 Phase 1 的正式交付物，不是附属说明

本次变更必须直接落地以下文档：
- `README.md`
- `docs/index.md`
- `docs/project-overview.md`
- `docs/technical-solution.md`
- `docs/decisions.md`
- `docs/run-and-deploy.md`

其中：
- `README` 用于项目入口和快速理解
- `project-overview` 说明产品目标、范围和非目标
- `technical-solution` 汇总技术架构和关键设计
- `decisions` 记录用户已拍板项
- `index` 作为文档列表
- `run-and-deploy` 覆盖本机快启、Compose 验收和基础部署说明

原因：
- 用户明确要求把“刚才讨论和排版的”都沉淀成文档
- 当前仓库为空，先建立文档骨架可以降低后续实现歧义

替代方案：
- 只在 OpenSpec 中记录：对未来使用者和实现者可见性不足
- 只写 README：无法承载这么多细节

## 风险 / 权衡

- [Cursor 登录状态和身份字段可能无法稳定提取] → 以 best-effort 展示为准，允许只展示已登录状态，并在文档里明确该限制
- [单容器内运行时安装会增加应用职责] → 保持安装器和 Cursor provider 边界清晰，避免把运行时逻辑散落到前端
- [普通提交也更新 `latest` 可能导致镜像漂移] → 当前仅围绕当前分支工作流使用，先接受这一取舍
- [官方 Compose 不带挂载会导致默认数据不持久] → 在 `run-and-deploy` 中清楚写明，需要持久化者自行加 mount
- [文档和实现同步成本增加] → 将文档编写列为本次首批任务，并在后续实现任务中要求同步更新文档

## Migration Plan

1. 创建并完成本次 OpenSpec 产出物：proposal、design、specs、tasks
2. 在仓库中建立文档骨架和 README，把已拍板项先固化下来
3. 搭建 monorepo 目录和最小应用骨架，保留 `desktop` 占位
4. 实现 Web 管理入口、Cursor 运行时安装/升级、账号引导、配置和 skill 管理
5. 补齐 `VERSION`、GitHub Actions、Dockerfile 和 Compose 示例
6. 通过本机开发态和 compose 验收两条入口验证系统可运行

回滚策略：
- 文档和仓库结构可直接通过 git 回滚
- 镜像问题可回滚到上一个 `X.Y.Z` 版本
- 运行时安装问题通过重建容器和清理受管目录恢复
